# 演出式 QTE — 实施计划

上游：[设计](design.md)。完整流程，已就绪，2026-10-13。

1. 在 Combat 中实现 QTE 模式、直接出牌及恢复剩余决策时间的规则；保留队列测试，补充拒绝输入、终止状态和阶段链测试（AC-01–03）。同时在场景／镜头文件中实现表现层机位、转换及独立生命周期测试（AC-04–05）。设计中约定固定，不交叉修改同一文件。
2. 根据快照约定集成浏览器按钮、键盘、模式选择和情境提示。旧浏览器测试显式选择队列模式，新增使用实际输入的 QTE 场景（AC-01–05）。
3. 主代理审查实际差异，执行严格类型检查、规则／镜头测试、生产构建和浏览器回归。在桌面视口采集多个行动分镜及未暂停的动作序列，检查威胁可见性和错误。修复具体缺陷，记录限制，再根据用户已有的直接提交 main 授权提交并推送。本地构建成功不代表托管部署成功。


## 2026-10-14 双方回合迁移

依据 [PRD](prd.md) FR-06–10、AC-06–09 和[设计](design.md)已确认规则，替代旧 Response 流程，不恢复旧状态行为。

1. 规则：扩展 `src/combat.ts` 的行动方、敌方 AP、待结算卡牌、回合结束边界和持有者冷却；修改纯规则测试验证恢复归属、无普通 Response、反击检查、格挡、非伤害牌及取消／暂停／重置。
2. 适配：修改 `src/main.ts`／`src/chinese.ts`／样式，明确回合及资源、更新操作文案和卡牌展示；镜头／场景识别回合结束，不改动已有机位、美术或粒子预算；更新快照测试数据。
3. 验证与交付：严格类型、单元、生产构建和实际输入浏览器检查；覆盖桌面即时／队列、反击冷却直结算、暂停／重开、减少动态效果及手机竖屏。审图、更新本轮证据后直接提交／推送 main。失败只针对原因修复，未验证托管部署不得宣称成功。

## 2026-10-15 连续出牌与顺序演出

采用完整流程，沿用现有 PRD FR-14–18／AC-12–16 和己方行动队列设计；不实现整套新分镜或增加资产。

1. 规则任务：`src/combat.ts`、`tests/combat.test.ts`。分离提交开关与 acting，入队即扣费／占用，效果在 0.55 秒生效一次，完整演出为 0.79 秒（含 0.24 秒收势）；统一两模式行动时长以保证动画衔接一致。暴露提交开关、冻结的选牌预算、未执行队列及当前行动是否已生效。关闭提交后排空再结束，终止／重开清理；保留旧预览模式与反击语义。先验证纯规则。
2. 集成任务：main／chinese／style、scene／camera 及浏览器／镜头测试。按钮与键盘在演出中接收合法输入，实时显示当前／等待行动和选牌预算，结束按钮关闭提交；场景在生效后完成收势，入队不触发镜头切换。检查手机布局、减少动态效果和无页面错误。
3. 主代理审查规则与集成差异，执行类型检查、单元、生产构建、真实输入浏览器检查；更新证据与状态，直接提交推送 main。本地构建、远端 CI 和 Pages 部署分别报告。

主要风险：入队未占用造成重复提交、扣费两次、动作结束提前切回合、收势期间重复伤害、HUD 误减预留 AP、动画阶段阻断键盘、暂停或致死遗留队列。
